# Kiln usage and efficiency

Every model call in Ploby goes through one client, [`pcp/kiln.py`](../pcp/kiln.py), to the Kiln API with `qwen3-32b` on every stage ([`pipeline.json`](../pipeline.json); the organizers moved the challenge from `gpt-oss-120b` to `qwen3-32b`, see [kiln-notes.md](kiln-notes.md)). The client logs each call by flow to `harness/runs/usage.jsonl`: Kiln's token counts, Kiln's reported cost, the measured latency and Kiln's generation id (`X-Neocloud-Generation-Id`, the evidence that the call reached the API). The tables below are that log as [`harness/usage_report.py`](../harness/usage_report.py) prints it. The script uses only the standard library, reads the local log and calls nothing. The live log and response cache are local. This page uses the committed, sanitized app-stage snapshot: run `python3 harness/usage_report.py --log evidence/usage.jsonl --md` to reproduce its tables. The committed evidence run ([evidence.md](evidence.md)) keeps the generation id and usage of every call it used in its project log.

**App flows** are Ploby's model stages ([`pcp/stages.py`](../pcp/stages.py)):

- `write`, `read` and `reread` turn the client's expense rules in words into a mandate ([`pcp/compiler.py`](../pcp/compiler.py)).
- `quote` reads a vendor's quote, invoice or receipt (`read_quote` in [`escrow/ai.py`](../escrow/ai.py)).
- `change` drafts a change order (`draft_change`); it has not been called yet.
- `agent` plans the contractor's purchase task ([`escrow/agent.py`](../escrow/agent.py)).

The team made every call while building, testing and demoing Ploby. **Development and evaluation flows** are the rule pipeline's earlier runs on its benchmark domains (shopping, compute), made before the pipeline moved into this repository. No code here makes them any more.

### Notes

- A row is one flow on one model; a local cache hit counts under the model of the call it replays. Reasoning tokens are part of completion tokens, provider-cached tokens part of prompt tokens. Latency is the client-measured round trip (network and queueing included).
- Cost: Kiln's reported usage.cost on 51 of 51 API calls.
- Kiln's cost equals (uncached prompt x $0.08 + cached prompt x $0.04 + completion x $0.28) per 1M tokens on 51 of 51 qwen3-32b calls with cached tokens: cached input is billed at half the input price (inferred from the bills; not published).
- Energy bound = cards x rated power x latency (qwen3-32b: 4 x FuriosaAI RNGD, 180 W TDP each; deepseek-v4.1-flash: 8 x AMD Instinct MI325X, 1,000 W max board power each).
- Energy estimate (qwen3-32b only): 0.060 J per prompt token the provider cache did not serve + 0.268 J (busy) to 6.06 J (alone) per completion token.


## Energy model

Kiln does not publish the hardware or power behind `qwen3-32b`, so none of these energy figures is a measurement of Kiln. Each one multiplies our measured latency or token counts by published hardware figures, under the assumptions below.

| Figure | Formula | What it means |
| --- | --- | --- |
| Bound | 4 cards × 180 W × measured latency = 720 W × latency | An upper bound: the whole model replica at rated power for the whole round trip. Kiln batches requests on a replica, and latency includes network and queueing time, so the true share is lower. |
| Estimate | 0.060 J × prompt tokens the provider cache did not serve + (0.268 J busy to 6.06 J alone) × completion tokens | Measured power and speed of Qwen3-32B FP8 on four RNGD cards. *Busy*: 256 concurrent requests share the replica. *Alone*: the request is the only one on it. |

| Input | Value | Source |
| --- | --- | --- |
| RNGD card power | 180 W TDP | FuriosaAI product page and specifications [1, 2]. The developer documentation lists 150 W [3]; we use the higher figure. |
| Cards per `qwen3-32b` replica | 4 | FuriosaAI's Qwen3-32B-FP8 build runs tensor parallel over 32 processing elements, "four RNGD cards (8 PEs per card)" [4]. LG AI Research also ran a 32B model at 16-bit on four RNGD cards [9]. |
| Four-card power | 436 W alone (concurrency 1), 692 W busy (concurrency 256) | Lablup and FuriosaAI benchmark of Qwen3-32B FP8, June 2026, Table 11 [5]: 109–173 W per card, within the TDP |
| Time to first token, 1,024-token prompt, alone | 0.14 s | Same benchmark, Table 12 |
| Time per output token | 13.9 ms alone, 99.2 ms busy | Same benchmark, Table 12 |
| Prefill energy per prompt token | 436 W × 0.14 s ÷ 1,024 = 0.060 J | Derived |
| Decode energy per completion token | 436 W × 13.9 ms = 6.06 J alone; 692 W × 99.2 ms ÷ 256 = 0.268 J busy | Derived |

Cross-check: the per-token figures reproduce the benchmark's own tokens per watt. Alone, 0.060 + 6.06 = 6.12 J per generated token, against 436 W ÷ 71 tok/s = 6.14 J. Busy, 0.33 J against 692 W ÷ 2,336 tok/s = 0.30 J, so ours runs about 10% high.

Assumptions (stated, not verified):

1. Kiln serves `qwen3-32b` on FuriosaAI RNGD the way FuriosaAI's published build does: four cards per replica, FP8. This follows the challenge brief and Kiln's own description, "AI inference API on NPUs" [6]. Kiln's catalog lists no hardware for `qwen3-32b` [7]. More cards per replica would raise the bound in proportion, and another precision would change the per-token figures.
2. Accelerator energy only. Host CPUs and memory, networking, cooling (PUE) and Kiln's gateway are not counted.
3. The benchmark used 1,024-token prompts with prefix caching off. Our prompts reach about 4,000 tokens and are mostly served by Kiln's prefix cache. A cached prompt token is charged no prefill energy because its KV entries are reused. The extra decode cost of a longer context is not modeled.
4. A local cache replay sends no inference request and has no additional provider charge. Local CPU, storage and network activity still consume energy; zero total energy is not claimed.

Per action, the decision uses no new model call; the initial document interpretation and optional receipt reading do. An agent task uses one plan plus readings for the documents it submits. The flow table gives the observed per-call latency and conditional energy figures. They do not establish hardware energy measured at Kiln.

## How the responses inform decisions

The payment rules run on the model's reading of the vendor document. The model copies the issuer and the amounts as the document writes them (`read_quote`). Code then maps the issuer to a registered vendor and its category, parses the amounts, and checks that each amount appears in the document and that amount + fee = total (`proposal_of`). The result is a proposal of merchant, category, item, amount, fee and units. The rules in `Expenses.evaluate` ([`escrow/expenses.py`](../escrow/expenses.py)) test that proposal:

- vendor and category against the signed mandate;
- amount + fee against the per-purchase limit;
- the budgets and the escrow balance.

The payee always comes from the policy. If code cannot trust a reading (it found a problem, or there is no reading), the evidence rule fails. The request is then held for the client, or blocked if a mandatory rule also fails, but never approved.

The agent's plan only sets the order in which documents are filed. Each engine decision drives the agent's next step: a BLOCK moves it to the plan's next offer, a HOLD makes it wait, and a paused project stops it (`Store.agent_run` in [`escrow/store.py`](../escrow/store.py)). In the evidence run, the Adobe Stock quote was read as 185,000 + VAT 18,500, and the per-purchase rule blocked it (203,500 > 200,000). The AWS invoice that carried a payment instruction was held on the price-anomaly signal, and its payee came from the policy, not the document ([evidence.md](evidence.md)).

## How the design avoids unnecessary inference

1. **No model call decides a payment.**
   - `Expenses.request` and `Expenses.evaluate` run the rules in code, on the reading already stored in the log line.
   - The mandate they run (`Core.mandate` in [`escrow/core.py`](../escrow/core.py)) is compiled once, when the project is created (`Store.compile_rules`, then `Store.create`, then `rules_of` in [`escrow/policy.py`](../escrow/policy.py)). Rules entered through the form need no model at all (`rules_from_form`).
   - When the client approves a HOLD, `op_answer_request` runs the rules again in code.
   - The only model call sites are `escrow/ai.py` (`quote`, `change`), `escrow/agent.py` (`agent`) and `pcp/compiler.py` (`write`, `read`, `reread`). No engine module (`escrow/engine.py`, `core.py`, `expenses.py`, `milestones.py`, `changes.py`, `policy.py`) calls the model.
   - A decision therefore costs 0 model calls.
2. **Exact readings can be cached; replay and audit never call the model.**
   - `Store.prepare` reads the document before the rules run and stores the reading in the line's `inputs`. `Store.replay` and `python3 -m escrow.audit` rebuild a project from its log alone.
   - The Kiln client caches every response under a hash of the exact request (`chat` in `pcp/kiln.py`, stored in `harness/runs/cache/`).
   - Measured: the committed app snapshot has 351 exact local cache replays. The matched eight-document experiment above makes the comparison reproducible; fresh-read benchmark calls deliberately bypass the local response cache.
   - The cache is local, and a rules compile includes the current minute in its prompt, so a compile is replayed only within the same minute.
3. **The fixed system prompt comes first, so the provider's prefix cache serves it.**
   - The quote prompt (`quote_prompt`, "first, so the prefix cache serves it"), the change prompt, the compiler's writer and reader prompts, and the agent's prompt all put the fixed text first. The compiler's prompt is followed by the time, the calendar and the words. `reread` continues the same conversation.
   - Measured: Kiln reported 27,308 of 62,495 prompt tokens as cached (44%) in the committed app snapshot. This is provider caching, separate from local replay.
   - Kiln bills a cached prompt token at half price (inferred from the reported cost of every logged call), and the energy model assumes reused KV entries avoid prefill; actual provider telemetry is unavailable.
4. **Reasoning only where it pays.**
   - `pipeline.json` turns thinking on for `reread` only. Every other stage appends `/no_think` (`thinking` in `pcp/kiln.py`).
   - The compiler runs the reasoning round only when the two blind readings disagree or code finds a fault in one, and only for the readings concerned (`compile_words` in `pcp/compiler.py`).
   - When qwen3 leaves the JSON answer at the end of its reasoning, `answer_in` takes it from there instead of paying for a re-ask.
   - Every stage caps its output with `max_tokens`: 800 for quote, 900 for change, 1,200 for agent, 4,000 for write and read, and 8,000 for reread.
   - Measured: every app call with thinking off reported exactly 1 reasoning token (the empty think block). The app's 2 reread calls made 640 of its 689 reported reasoning tokens (93%). Of the two escrow compiles sent live, one agreed at once (2 calls) and one escalated (4 calls).
5. **A failure becomes HOLD, not a retry loop.**
   - `reading` in `escrow/ai.py` turns any exception (network, rate limit or budget guard) into an unavailable reading. `fields_of` in `escrow/expenses.py` then holds the request as POLICY_OR_SYSTEM_AMBIGUITY.
   - `read_quote` re-asks at most once when the reply is not one JSON object, then holds the request as EVIDENCE_DEFECT.
   - `draft_change` and the agent's `plan` make one call each and hand a failure back to the person.
   - A compile retries a reading that does not build at most twice, and once more in the reasoning round. After that it points to the rules form.
   - `pcp/kiln.py` retries only transport failures (HTTP 429, 5xx and connection errors), with at most six attempts in all. Kiln's error table lists 429, 502 and 503 as not billed ([kiln-notes.md](kiln-notes.md)).
   - Three budget guards (per run $0.50, logged total $5, key total $80) refuse a call before it is sent.
6. **The agent plans once.** `Store.agent_run` asks the model for one plan per task and files the plan's first offer for each need as an ordinary request. On a BLOCK it moves to the plan's next offer without asking the model again. In the evidence run, six tasks made six plan calls ([evidence.md](evidence.md)).
7. **The accepted low-cost model is used consistently.** Every app stage runs `qwen3-32b` in `pipeline.json`. The team confirmed both qwen3-32b and deepseek-v4.1-flash are allowed. Earlier experiments compared different settings and corpora, so they are not used as an accuracy or energy superiority claim.

## What we could not verify

- Kiln does not publish the hardware, precision or batching behind `qwen3-32b`. Every energy figure here is an estimate under the assumptions above, not a measurement.
- The cached-input price (half the input price) is inferred from Kiln's reported costs. Kiln does not publish it.
- The committed app snapshot is not a randomized quality evaluation. The benchmark fixtures are declared and limited to the application examples.
